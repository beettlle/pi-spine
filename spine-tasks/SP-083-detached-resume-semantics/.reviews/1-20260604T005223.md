## Plan Review: Wait semantics (Step 1)

### Verdict: REVISE

### Summary

The wait-semantics design is directionally correct: default detached start/resume should return `{ ok: true, status: "engine_started" }` once batch-state shows a fresh `running` transition, while `--wait-terminal` should block until `evaluateDetachedResumeWait` sees batch terminal, `paused`, or the resumed task reaches a terminal task status — then return `resume_completed` / `start_completed`. Wiring `waitTerminal` through `parseBatchArgs`, `startBatchDetached`, and `resumeBatchDetached`, plus distinct success headlines in `formatDetachedEngineOutput`, matches the PROMPT mission.

The worktree plan is not yet safe to execute as Step 1: it omits the required runbook documentation and bundles Step 2 failure-surfacing work (`readLastTaskFailedEvent`, diagnostics collectors, failure log tails, timeout diagnose messaging) into the same diff. Tighten the Step 1 boundary before implementation or commit.
