The core fix — relaxing the `codeReviewAttempt === 0` / `finalAttempt === 0` guard — is correctly implemented and achieves the primary self-healing goal: on `spine batch resume`, the engine re-enters `runCodeReviewPhase`/`runFinalReviewPhase` and honors existing artifacts regardless of attempt count. Two non-blocking observations are noted below.

**Observation 1 — `reconcileOrphanedReviewEvents` is not wired into any production path.** The function is exported from `journal-rebuild.mjs` and tested, but no production code imports or calls it (only `tests/batch/review-crash-recovery.test.mjs` consumes it). The Completion Criteria ("spine batch resume auto-heals tasks stuck after review.started crash") are met by the relaxed attempt guard alone, so this is not blocking. However, the PROMPT Mission #1 says "On `spine batch resume`, detect orphaned `review.started` events… synthesize the missing `review.completed` + `task.completed` events," which implies wiring the reconciler into the resume/rebuild flow (e.g. `reconcile.mjs` or `rebuildBatchStateFromJournal`). Consider filing this as a follow-up to wire `reconcileOrphanedReviewEvents` into the journal rebuild path so the journal is self-consistent even before the engine re-runs the review phase.

**Observation 2 — `detectOrphanedReviewStarted` under-detects in retry-after-REVISE scenario.** The `completedKeys` set records any key that has *ever* had a `review.completed`. If a review completes with REVISE, then the task retries, then the engine crashes after the second `review.started`, the second orphan will NOT be detected because `completedKeys` still contains the key from the first completion. This edge case is unlikely in the SP-484 crash scenario (which targets first-cycle crashes), and the relaxed guard handles it at the engine level regardless. Not blocking.
